Phase 1 — Step 1: Requirements Analysis

1.1 Project Description

Keşfet Türkiye ("Discover Turkey") is a web-based travel-guide platform focused entirely on Turkey. Registered users can explore cities and tourist attractions, write and read reviews, build personalised travel itineraries, upload photos, and save favourite destinations. An administrator panel provides moderation and platform-wide statistics. The system is backed by an SQLite relational database and a Flask REST API.

1.2 Main Application Functions

  1. City & Place Browsing — Users can browse all Turkish cities (filtered by region or tag) and the popular attractions within each city.
  2. User Registration & Authentication — Visitors can create an account, log in, update their profile (bio, location, avatar colour), and log out.
  3. Reviews & Ratings — Authenticated users write text reviews and give star ratings (1–5) for cities. Reviews can be edited or deleted by their author.
  4. Review Likes — Users can like other users' reviews, creating a social engagement layer.
  5. Favourites — Users can mark cities as favourites for quick access later.
  6. Travel Plan Builder — Users create named trip plans, set travel dates, and add ordered city stops with personal notes.
  7. Photo Gallery — Users upload photos (jpg/png/webp) tagged to specific cities.
  8. City View Tracking — Each time a city detail page is opened, the system increments a view counter, generating passive popularity data.
  9. Notifications — The platform sends in-app notifications for key events (new favourite, review like, trip creation, photo upload).
  10. Admin Panel — Admins manage users (role promotion, deletion), moderate reviews, and view aggregated platform statistics.
  11. Full-text Search — Users can search cities and places by name, region, or description.

1.3 How the Functions Work Together

A user first browses the city/place catalogue (function 1). If they wish to contribute, they register (function 2). Once logged in they can write reviews (3), like others' reviews (4), save favourites (5), build a trip (6), upload photos (7), and receive notifications (9) for social interactions. The view-tracking counter (8) runs silently in the background every time any user opens a city page. The admin role (10) sits on top of the same data and consumes aggregated queries against all tables. Search (11) queries the same city and place tables without authentication.

All functions converge on the same relational database. The most interesting analytical value comes from cross-table aggregations: which cities attract the most reviews, who are the most active users, which places appear in the most travel plans, etc.

1.4 Data Needed to Support the Functions

  • City data: identifier, name, geographic region, description, category tags
  • Tourist place data: name, parent city, category, rating, description
  • User data: credentials, profile (bio, location, avatar), role, registration date
  • Reviews: author, target city, star rating (1–5), review text, timestamp
  • Review likes: which user liked which review, timestamp
  • Favourites: which user saved which city, timestamp
  • Trips: owner, title, start/end dates, description, creation timestamp
  • Trip stops: linked trip, ordered list of city stops, optional notes
  • Photos: uploader, city, file path, caption, upload timestamp
  • City view counters: per-city integer counter
  • Notifications: recipient user, message text, optional link, read/unread flag, timestamp

1.5 Interesting Database Queries

The following queries cannot be answered by simply reading a single stored value; they must be derived by aggregating or joining stored data — demonstrating strong database support value.

Query 1 — Which city has the highest average user rating?

This identifies the most highly-praised destination, useful for featured recommendations.

SELECT city_name, ROUND(AVG(rating), 2) AS avg_rating, COUNT(*) AS review_count FROM reviews GROUP BY city_name HAVING COUNT(*) >= 3 ORDER BY avg_rating DESC;

Query 2 — Top 5 most-visited cities (by page-view count)

Reflects organic user interest; helps highlight trending destinations on the home page.

SELECT c.name, c.region, cv.view_count FROM cities c JOIN city_views cv ON cv.city_id = c.id ORDER BY cv.view_count DESC LIMIT 5;

Query 3 — Which cities appear most often in travel plans?

Aggregates across users' itineraries to find destinations people actually plan to visit.

SELECT ts.city_name, COUNT(*) AS plan_appearances FROM trip_stops ts JOIN trips t ON t.id = ts.trip_id GROUP BY ts.city_name ORDER BY plan_appearances DESC;

Query 4 — Ranking of users by total engagement (reviews + favourites + trips)

Identifies the platform's most active contributors for potential gamification rewards.

SELECT u.username, COUNT(DISTINCT r.id) AS reviews_written, COUNT(DISTINCT f.id) AS cities_favourited, COUNT(DISTINCT t.id) AS trips_created, (COUNT(DISTINCT r.id) + COUNT(DISTINCT f.id) + COUNT(DISTINCT t.id)) AS total_engagement FROM users u LEFT JOIN reviews r ON r.user_id = u.id LEFT JOIN favorites f ON f.user_id = u.id LEFT JOIN trips t ON t.user_id = u.id GROUP BY u.id ORDER BY total_engagement DESC;

Query 5 — Which cities have the most user-uploaded photos?

Shows where the community generates visual content; can drive photo-featured city pages.

SELECT p.city_name, COUNT(*) AS photo_count, COUNT(DISTINCT p.user_id) AS contributing_users FROM photos p GROUP BY p.city_name ORDER BY photo_count DESC;

Query 6 — Most-liked reviews (with reviewer and city)

Surfaces the highest-quality review content for featured placement.

SELECT r.reviewer_name, r.city_name, r.rating, r.text, COUNT(l.id) AS like_count FROM reviews r LEFT JOIN review_likes l ON l.review_id = r.id GROUP BY r.id ORDER BY like_count DESC LIMIT 10;

Query 7 — Average trip length (number of stops) per user

Helps understand how deeply users plan and whether multi-city itineraries are common.

SELECT u.username, COUNT(ts.id) / NULLIF(COUNT(DISTINCT t.id), 0) AS avg_stops_per_trip, COUNT(DISTINCT t.id) AS trip_count FROM users u JOIN trips t ON t.user_id = u.id JOIN trip_stops ts ON ts.trip_id = t.id GROUP BY u.id HAVING trip_count > 0 ORDER BY avg_stops_per_trip DESC;

Query 8 — Cities that appear in favourites but have zero reviews (content gap)

Reveals popular cities that still lack user-generated review content — marketing opportunity.

SELECT c.name, COUNT(DISTINCT f.user_id) AS favourite_count, COUNT(DISTINCT r.id) AS review_count FROM cities c LEFT JOIN favorites f ON f.city_id = c.id LEFT JOIN reviews r ON r.city_id = c.id GROUP BY c.id HAVING review_count = 0 AND favourite_count > 0 ORDER BY favourite_count DESC;

Phase 1 — Step 2: Entity-Relationship (E/R) Diagram

2.1 Overview of the Conceptual Design

The central entity of the model is City. A city contains many Places (tourist attractions). Users interact with cities in three ways: they write Reviews, mark them as Favourites, and include them as stops in Trips. Users also interact with each other's reviews through Review Likes. They contribute Photos attached to cities. The system tracks how many times each city page has been opened via CityViews. Lastly, the platform sends Notifications to users.

All relationships and their cardinalities are explained in Section 2.3 and depicted in the E/R diagram below.

Phase 2 — Database Design: Relational Schema

3.1 Mapping Algorithm Applied to the E/R Diagram

The following mapping rules (as taught in class) were applied:

  1. Each regular entity becomes a relation with all its attributes. The primary key of the entity is the primary key of the relation.
  2. Each weak entity becomes a relation. Its primary key is the combination of its partial key and the primary key of the owner entity.
  3. Each 1:N relationship is represented by adding a foreign key in the "many" side relation pointing to the "one" side.
  4. Each M:N relationship produces a new relation whose primary key is the combination of the two participating entities' primary keys. Extra relationship attributes are included.
  5. Each 1:1 relationship can be merged into either side as a foreign key; here CityViews is kept as a separate table with city_id as both PK and FK.

3.2 Relational Schema (SQL CREATE TABLE Statements)

-- ─────────────────────────────────────────────────────────────────────────
-- TABLE: cities
-- Maps to: City entity
-- ─────────────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS cities (
    id          INTEGER PRIMARY KEY,
    name        TEXT    UNIQUE NOT NULL,
    region      TEXT    NOT NULL,
    description TEXT,
    tags        TEXT        -- comma-separated category tags (e.g. 'Tarih,Müze')
);

-- ─────────────────────────────────────────────────────────────────────────
-- TABLE: city_views
-- Maps to: CityViews weak entity (1:1 with City, owner = City)
-- ─────────────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS city_views (
    city_id     INTEGER PRIMARY KEY,
    view_count  INTEGER NOT NULL DEFAULT 0,
    FOREIGN KEY (city_id) REFERENCES cities(id) ON DELETE CASCADE
);

-- ─────────────────────────────────────────────────────────────────────────
-- TABLE: places
-- Maps to: Place entity + CONTAINS(City,Place) 1:N → FK city_id here
-- ─────────────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS places (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    name         TEXT    NOT NULL,
    city_id      INTEGER NOT NULL,
    city_name    TEXT    NOT NULL,       -- denormalized for display performance
    category     TEXT    NOT NULL,       -- human-readable label (e.g. 'Tarihi Yer')
    category_key TEXT    NOT NULL,       -- CSS/filter key (e.g. 'tarih')
    rating       REAL    NOT NULL DEFAULT 0.0,
    description  TEXT,
    icon         TEXT,
    img_key      TEXT,
    FOREIGN KEY (city_id) REFERENCES cities(id) ON DELETE CASCADE
);

-- ─────────────────────────────────────────────────────────────────────────
-- TABLE: users
-- Maps to: User entity
-- ─────────────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS users (
    id           INTEGER  PRIMARY KEY AUTOINCREMENT,
    username     TEXT     UNIQUE NOT NULL,
    email        TEXT     UNIQUE NOT NULL,
    password     TEXT     NOT NULL,          -- bcrypt hash
    role         TEXT     NOT NULL DEFAULT 'user'
                          CHECK (role IN ('user', 'admin')),
    bio          TEXT,
    location     TEXT,
    avatar_color TEXT     NOT NULL DEFAULT '#C1272D',
    created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- ─────────────────────────────────────────────────────────────────────────
-- TABLE: reviews
-- Maps to: Review entity
--          + WRITES(User,Review)   1:N → FK user_id
--          + REVIEWS(Review,City)  N:1 → FK city_id
-- ─────────────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS reviews (
    id            INTEGER  PRIMARY KEY AUTOINCREMENT,
    city_id       INTEGER  NOT NULL,
    city_name     TEXT     NOT NULL,           -- denormalized for display
    reviewer_name TEXT     NOT NULL,
    rating        INTEGER  NOT NULL
                           CHECK (rating >= 1 AND rating <= 5),
    text          TEXT     NOT NULL,
    user_id       INTEGER,                     -- NULL for anonymous seed data
    created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (city_id)  REFERENCES cities(id) ON DELETE CASCADE,
    FOREIGN KEY (user_id)  REFERENCES users(id)  ON DELETE SET NULL
);

-- ─────────────────────────────────────────────────────────────────────────
-- TABLE: review_likes
-- Maps to: LIKES(User,Review) M:N relationship
-- ─────────────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS review_likes (
    id         INTEGER  PRIMARY KEY AUTOINCREMENT,
    user_id    INTEGER  NOT NULL,
    review_id  INTEGER  NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (user_id, review_id),               -- one like per user per review
    FOREIGN KEY (user_id)   REFERENCES users(id)   ON DELETE CASCADE,
    FOREIGN KEY (review_id) REFERENCES reviews(id) ON DELETE CASCADE
);

-- ─────────────────────────────────────────────────────────────────────────
-- TABLE: favorites
-- Maps to: FAVOURITES(User,City) M:N relationship
-- ─────────────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS favorites (
    id         INTEGER  PRIMARY KEY AUTOINCREMENT,
    user_id    INTEGER  NOT NULL,
    city_id    INTEGER  NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (user_id, city_id),                 -- one favourite entry per pair
    FOREIGN KEY (user_id) REFERENCES users(id)   ON DELETE CASCADE,
    FOREIGN KEY (city_id) REFERENCES cities(id)  ON DELETE CASCADE
);

-- ─────────────────────────────────────────────────────────────────────────
-- TABLE: trips
-- Maps to: Trip entity + CREATES(User,Trip) 1:N → FK user_id
-- ─────────────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS trips (
    id          INTEGER  PRIMARY KEY AUTOINCREMENT,
    user_id     INTEGER  NOT NULL,
    title       TEXT     NOT NULL,
    start_date  TEXT,                          -- ISO date string YYYY-MM-DD
    end_date    TEXT,
    description TEXT,
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

-- ─────────────────────────────────────────────────────────────────────────
-- TABLE: trip_stops
-- Maps to: INCLUDES(Trip,City) M:N + TripStop weak entity attributes
-- ─────────────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS trip_stops (
    id         INTEGER  PRIMARY KEY AUTOINCREMENT,
    trip_id    INTEGER  NOT NULL,
    city_id    INTEGER  NOT NULL,
    city_name  TEXT     NOT NULL,              -- denormalized for display
    stop_order INTEGER  NOT NULL DEFAULT 0,    -- ordering within the trip
    notes      TEXT,
    FOREIGN KEY (trip_id) REFERENCES trips(id)   ON DELETE CASCADE,
    FOREIGN KEY (city_id) REFERENCES cities(id)  ON DELETE CASCADE
);

-- ─────────────────────────────────────────────────────────────────────────
-- TABLE: photos
-- Maps to: Photo entity
--          + UPLOADS(User,Photo)      1:N → FK user_id
--          + TAGGED_TO(Photo,City)    N:1 → FK city_id
-- ─────────────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS photos (
    id         INTEGER  PRIMARY KEY AUTOINCREMENT,
    user_id    INTEGER  NOT NULL,
    city_id    INTEGER  NOT NULL,
    city_name  TEXT     NOT NULL,              -- denormalized for display
    file_path  TEXT     NOT NULL,
    caption    TEXT,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id)  ON DELETE CASCADE,
    FOREIGN KEY (city_id) REFERENCES cities(id) ON DELETE CASCADE
);

-- ─────────────────────────────────────────────────────────────────────────
-- TABLE: notifications
-- Maps to: Notification entity + RECEIVES(User,Notification) 1:N → FK user_id
-- ─────────────────────────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS notifications (
    id         INTEGER  PRIMARY KEY AUTOINCREMENT,
    user_id    INTEGER  NOT NULL,
    message    TEXT     NOT NULL,
    link       TEXT,
    is_read    INTEGER  NOT NULL DEFAULT 0
                        CHECK (is_read IN (0, 1)),
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

3.4 Integrity Constraints Summary

  • NOT NULL: All primary keys, foreign keys, and business-critical fields (username, email, password, city name, review text, rating).
  • UNIQUE: username, email in users; (user_id, city_id) in favorites; (user_id, review_id) in review_likes.
  • CHECK: rating between 1–5 in reviews; is_read in {0,1}; role in {'user','admin'}.
  • FOREIGN KEY with ON DELETE CASCADE: deleting a user cascades to their reviews, favorites, trips, photos, notifications, and review_likes; deleting a trip cascades to its stops.
  • FOREIGN KEY with ON DELETE SET NULL: deleting a user sets user_id = NULL on reviews authored anonymously, preserving the review content.
